# GEL RAM v0.7.0 — no third-party packages, one Unicode version, and the same output bits on faster paths

Date: 2026-10-31

v0.7.0 collects everything merged after v0.6.1 (pull requests #72 to #89).
gel-source now computes SHA-256 and Unicode NFC itself, so `Cargo.lock` lists
no third-party package. NFC follows Unicode 16.0.0, the version the pinned Rust
1.85.0 standard library uses for lowercasing and word splitting, so the whole
search path follows one Unicode version. Many paths are faster while every
output bit stays the same, a bundle or collection load needs about half the
memory, and a published digest can now fix the exact contents of a directory
that is not published. The Rust pin stays 1.85.0; the workspace version moves
to 0.7.0. Every change is listed with its pull request in the
[roadmap](https://github.com/Gelram-project/gel-ram/blob/v0.7.0/docs/ROADMAP.md).

## What the project is

GEL RAM prints knowledge into memory as fixed Q8 records, instead of training it
into model weights, and reads the records back exactly, working toward
hardware-level memory computation. The goal is a text AI that answers in Polish
and English from what it holds, or says it does not know. **The text AI is a
goal, not a result of this repository**, and hardware-level memory computation
is not established: the claim registry lists it as `NOT_ESTABLISHED`. The step
that prints text into records is private, so the Q8 records in this checkout
hold synthetic values or literal bytes.

## No third-party packages

- Own SHA-256 (FIPS 180-4, safe Rust) and own Unicode NFC, generated byte for
  byte from unchanged UCD files in CI (#72, #73, #74).
- `cargo tree` lists no third-party package for any target.
- Cost: v0.6.1 hashed with the processor's SHA instructions through the sha2
  crate. The portable SHA-256 without `unsafe` is slower: against v0.6.1,
  SHA-256 alone runs at 0.28 and 0.39 of its speed, and paths that hash the
  whole input from 0.27 (A/A 0.96 to 0.98 and 0.81 to 1.25).

## One Unicode version on the search path

- NFC tables from UCD 16.0.0 (#88). Every line of NormalizationTest-16.0.0
  passes; every line of NormalizationTest-15.1.0 gives the same result as
  before, and every code point assigned in 15.1.0 keeps its properties.
- Text made only of characters assigned in Unicode 15.1 matches exactly as in
  v0.6.1; matching can differ only on characters assigned in Unicode 17.0.

## The same output bits, faster

Three speed packages (#82, #87, #89). Each change has a timing example in
`docs/SPEED.md`, and was timed with `xtask speed-ab` against two copies of the
baseline, 3 rounds with the order rotated, medians, on one 24-thread Linux
machine; every run printed the same output digest in all three trees, except
the whole-tree gates, which count the files of their own tree (below).
Speed-up is the baseline time divided by the new time; A/A is the second copy
of the baseline divided by the first, the noise to read each ratio against.

Against v0.6.1 (2026-10-20, other work loading the machine):

| Area | Speed-up | A/A |
|---|---|---|
| CRC-64 | 4.9 to 47.8 | 0.95 to 1.00 |
| Store build, open, verify and write | 4.8 to 46.5 | 1.01 to 1.14 |
| Structural encode | 1.4 to 103 | 0.96 to 1.02 |
| Q8 read and scan | 1.3 to 5.7 | 0.94 to 1.05 |
| Document and collection search | 1.4 to 14.8 | 0.95 to 0.97 |
| NFC-heavy lines and documents | 1.0 to 29 | 0.89 to 1.07 |
| Whole `gel-bench` run | 3.1 to 3.9 | 0.99 to 1.01 |
| SHA-256 | **0.28 and 0.39** | 0.96 to 0.98 |
| Paths that hash every byte | **0.27** to 6.5 | 0.81 to 1.25 |

Packages 2 and 3 on a quiet machine (2026-10-25 and 2026-10-31, no other
measurement running):

| Area | Speed-up | A/A |
|---|---|---|
| `--literal` | 1.28 to 9.47 | 0.99 to 1.02 |
| Repeated passage ranges | 8.8 to 24.0; distinct ranges 0.97 to 1.00 | 0.99 to 1.05 |
| gel-bench checks | 1.23 to 1.60 | 0.97 to 1.03 |
| Store open and verify (after #89, against before #87) | open 1.13 to 1.18; verify from 16 MiB 1.20 to 1.65; v1 verify 1.08 | 0.99 to 1.01 |

- After #87 the v1 store check ran at 0.64 of its earlier speed: its single
  digest ran on a new thread, and this machine has 8 logical CPUs at up to
  5.16 GHz and 16 at up to 3.29 GHz. In #89 the calling thread digests again;
  the v1 check is back to 1.08.
- A bundle load needs no second copy of its text: peak resident memory of a
  64 MiB load 134 072 KiB to 68 612 KiB, time 1.06 (A/A 0.99) (#89).
- A collection snapshot load keeps its document texts in one shared buffer
  instead of copying them: peak resident memory of a 64 MiB load 133 160 KiB to
  68 640 KiB, time 0.99 at 64 MiB and 1.09 at 32 MiB (A/A 0.96 to 1.04). A
  loaded document that is replaced or removed keeps its bytes in that buffer
  while any document of the same load lives (#89).
- The whole-tree gates of `xtask verify` share one walk of the tree: 1.23 to
  6.1 against v0.6.1 (A/A 0.93 to 1.03) (#82).

The manifests, summaries and every run's output are in
`docs/speed-results/2026-10-20-against-v0.6.1/` and
`docs/speed-results/2026-10-25-quiet-machine/`.

## Evidence you can rebuild

- `xtask witness NEW_DIR`: one command, one block with its own SHA-256 (#77).
- `xtask rebuild-check NEW_DIR`: the release package built twice and compared
  byte for byte (#78).
- `xtask commitment` / `commitment-check`: a SHA-256 published now that fixes a
  directory that is not published (#81); seven commitments listed in
  `docs/COMMITMENTS.md` (#81, #84, #85). A commitment says nothing about what
  the contents are or whether they are correct.

## Changed counting and documents

- answer-bench counts a returned passage that is the question's own source, or
  that answers a question the bank does answer, apart from errors (#76).
- The goal is stated once, in `docs/GOAL.md` (#75).
- The collection-review fixture cut to the scope and limits of a withdrawn
  bundle; all 24 cases give the same result (#86).
- CI: control kills of the history crash series drawn from inside the control
  run; 40 minutes for the portable build (#83).

## Verify this release yourself

```text
git clone https://github.com/Gelram-project/gel-ram.git
cd gel-ram
git checkout v0.7.0
rustup toolchain install 1.85.0 --profile minimal --component rustfmt --component clippy
cargo fetch --locked
cargo run --locked --offline -p xtask -- verify
cargo run --locked --offline --release -p gel-live-lab -- --witness
```

Expected final markers: `GEL_VERIFY_ALL=PASS` and `WITNESS=MATCH`.
`SOURCE-SHA256SUMS.txt` lists every other tracked file of the tagged tree. The
release asset GEL-RAM-v0.7.0-SOURCE.zip is `git archive` of the tagged commit;
its SHA-256 is published next to it. Binary packages are built in CI and carry a
build-provenance attestation, as described in
[binaries](https://github.com/Gelram-project/gel-ram/blob/v0.7.0/docs/BINARIES.md).

## Not claimed

No semantic chatbot, general AI, unrestricted question answering, measured
conversation, private engine or bank, hardware-level memory computation, speed
advantage over grep or any language model, or commercial superiority is claimed.
Timings are medians on one machine with an A/A control, not pinned to cores;
other machines and CI runners differ, and the 2026-10-20 runs were on a loaded
machine, so each ratio is read against its A/A column. The private printing
step and the private data sets are not part of this release; the commitments
only fix their contents. Four views of one record are not four independent
memories, four votes or a 4× speedup. A process kill or stop is not a power
cut; power-loss safety is not established. Answering natural questions remains
open: GEL answers a minority of them, and a 99% precision is not claimed.
